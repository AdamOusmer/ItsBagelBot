# Trial channel observation

Status: implemented; new trial channels start on and the admin per-channel toggle controls admission. Owner: Twitch ingress. Storage recovery wording reflects the deployed Valkey topology.

## Goal and language

An administrator can observe chat from up to four Twitch channels whose broadcasters have not registered with ItsBagelBot. The bot receives these messages through Twitch `channel.chat.message` EventSub, sends them through the existing ingress routing and Sesame processing paths, and records the work they cause. It sends no chat, moderation, redemption, clip, or other Twitch action on behalf of a trial channel. Registration ends the trial automatically; normal onboarding then controls the real channel.

`Trial channel` has the meaning in `CONTEXT.md`. `Registered` means a row exists in the users service; `active` or `onboarded` are separate user settings. A trial's Twitch ID is its identity, never its login. A trial message keeps its provenance even after the ID is removed from the trial list.

## Existing constraints

- The production Conduit uses an app access token. Twitch requires the broadcaster's `channel:bot` grant or bot moderator status for `channel.chat.message` on that transport. Trial chat instead needs an EventSub WebSocket subscription made with the bot account's user token carrying `user:read:chat`. The broadcaster supplies no grant. Twitch can still reject a subscription when the bot account is banned or timed out in that channel.
- Ingress has the normal `Ingress.Dispatcher` and `Ingress.Pipeline` path. Unknown broadcasters ordinarily use the standard lane, while messages from configured special chatters use premium. The trial receiver hands Twitch's normal notification shape to this path, preserving the EventSub notification ID, `event.message_id` (the chat message ID), and timestamp as separate values; it must not publish a handcrafted Sesame envelope directly.
- Outgress currently treats an unknown channel as enabled for chat. A missing registry row cannot provide the output block.
- Sesame currently increments the fleet and channel `messages_processed` counters on every decoded envelope, before module execution. The channel split drives a public leaderboard. Trial messages must be visible in fleet throughput while remaining distinguishable in trial reporting.
- Users service publishes `data.users.changed` after `Register`; that event includes the Twitch user ID but does not distinguish first registration from later updates. Ingress must treat any matching ID as registered and remove it idempotently. A periodic existence check covers missed events and restarts.
- Outgress owns and refreshes the bot account's user token. Ingress and Valkey must not receive the refresh token or persist access tokens. A narrowly authorized internal RPC lets the ingress owner ask outgress to create/delete the WebSocket EventSub subscription for a session ID using that token.

## Admin contract and authority

The admin page has a Trial channels section with an ID input, four-row ceiling, add/remove controls, and a per-channel on/off toggle. New rows start on. A row stays configured and counts toward the four-channel ceiling while off; its counters and display name remain visible. Observed state is pending, receiving, disabled, stopping, promoted, or failed with a short error. The page shows received, decoded, processed, failed/retried, blocked-action counts, and average processing latency for each ID. Mutations use the existing server-side admin role check and audit log; the browser never talks to ingress or Valkey directly. The ingress Shards preview also shows trial channels as distinct streamer rows, including whether each is on or off. Their primary label is Twitch display name, with numeric broadcaster ID secondary; they are not numbered or counted as Conduit shards. Outgress resolves a display name through Twitch when creating a subscription and ingress may refresh it from later chat events. An ID is the fallback only while a name is unavailable.

New RPC verbs (versioned request/reply DTOs in a shared contract):

| Verb | Request | Reply |
| --- | --- | --- |
| `twitch.ingress.admin.trials.list` | `{}` | desired IDs, display names, enabled flag, observed state, version, counters |
| `twitch.ingress.admin.trials.add` | `{broadcaster_id}` | accepted enabled pending state or explicit `invalid_id`, `already_registered`, `full`, `unavailable` |
| `twitch.ingress.admin.trials.set_enabled` | `{broadcaster_id, enabled}` | saved enabled flag and observed state; duplicate requests are idempotent |
| `twitch.ingress.admin.trials.remove` | `{broadcaster_id}` | accepted stopping state; removal is idempotent |
| `bagel.rpc.outgress.trial_subscription.create` | `{broadcaster_id, session_id, owner_epoch, trial_generation}` | subscription ID or Twitch rejection |
| `bagel.rpc.outgress.trial_subscription.delete` | `{broadcaster_id, subscription_id, owner_epoch, trial_generation}` | deleted/already absent or retryable error |

The admin server derives and audits the actor ID from its authenticated session; the browser does not choose it. The ingress RPC acknowledges a saved desired-state change, not completed Twitch setup. The page reads observed state until it becomes receiving or failed. All RPCs are bounded, and the NATS account permissions permit only the listed callers and subjects. The outgress RPC uses the existing bot-token source and fixed chat subscription type. It verifies the active owner epoch and trial generation against the Valkey record, stores the returned subscription ID with its session, and deletes only subscriptions recorded as owned by that trial; callers cannot name arbitrary Twitch subscriptions or sessions.

## Desired state and ownership

Valkey holds the small desired set of at most four numeric broadcaster IDs, a monotonically increasing revision, per-ID trial generation, each row's enabled flag, subscription ownership, and observation status. The trial control store holds no OAuth token or chat text; ordinary processing infrastructure still carries chat payloads. The deployed Valkey uses replicated memory with temporary disks: this state survives ingress restarts and ordinary member failover, but a complete Valkey cluster loss clears the trial list. The admin must re-add those IDs; no trial receiver resumes from an empty store. This is an accepted recovery limit for the four-channel experiment, not a claim of durable disk storage. An atomic Valkey operation reserves a pending slot under the four-ID cap and handles duplicates. A users-service existence RPC cannot be part of that atomic operation: check before and after reservation, and again before subscription activation. A concurrent registration can briefly coexist with pending trial state; user-change reconciliation cancels it, and trial provenance blocks every output in the meantime. Removing an ID is idempotent. Ingress needs an explicitly configured Valkey client, credentials and network permission.

One `TrialReceiver` owns one EventSub WebSocket while an enabled trial channel needs it, and closes it after the final active subscription stops. Ownership uses a renewable Valkey lease and monotonically increasing epoch; a lease loser stops forwarding and closes its socket, and outgress rejects stale-epoch subscription calls. It obtains a `session_id` from Twitch, asks outgress to create the chat subscriptions, and forwards notifications to `Ingress.Dispatcher`. On a Twitch-directed reconnect it transfers to the replacement socket without recreating subscriptions; after a fresh session following failure/restart it recreates subscriptions for that session. It reconciles against Valkey after restart and reports per-ID errors. Subscription rejection affects only the corresponding row. A failed Valkey read pauses new trial admissions and forwarding until ownership can be confirmed, rather than inventing an empty list or letting an old ID lose its output block.

The owner reconciles an off toggle by atomically fencing admission for that ID, deleting its recorded EventSub subscription, and retaining its configured row and counters. A frame already received after the toggle cannot pass the authoritative enabled and generation check, even if a receiver has a stale snapshot. Re-enabling while deletion is in flight waits for that deletion to finish before creating a replacement subscription. Removal also fences admission, then retains a stopping tombstone until deletion is confirmed. Each notification is tagged with trusted `origin=trial` and its generation at the receiver before dispatch; an external EventSub payload cannot set either. Provenance survives lane encoding, Sesame decode, cohorts, retries, batch children, and outgress construction. The current inline AutoMod path in Sesame does not run stateful moderation for trial messages. If AutoMod V2 is enabled later, its wrapper and Rust runtime must preserve provenance and enforce the same read-only rule before that route serves trial chat. Squash keys include origin and trial generation so normal and trial chat cannot share a cohort.

There is no deployment-wide trial admission flag. Once the ingress, Sesame, and outgress images are rolled out, the admin can add a channel and it starts on without an environment change. The per-channel admin toggle is the only intentional admission switch. Existing safety rules still reject registered IDs, stale owners, invalid subscriptions, and any trial-origin Twitch output. Outgress refuses output on provenance alone and never reads trial membership on the send path, so every Sesame replica must run the provenance-aware image before a trial is switched on: an older Sesame would emit untagged replies. An off row remains in the four-channel set until an admin removes it.

A bounded shared dedup window before squash uses `(broadcaster_id, event.message_id)` on both EventSub transports. The first admitted copy determines provenance, so a normal copy of a trial-admitted chat message is suppressed. Dedup failure must not turn a trial-origin message into a normal one; report the failure and retain suppression. This is bounded retry protection, not a promise of exactly-once processing after every crash.

## Processing and effects

Trial chat follows the normal lane selection, squash, and Sesame pipeline as ordinary unknown broadcasters. Trial mode does not create a users-service row or enable opt-in modules. It does not write channel-owned economy, command-use, or configuration state. Any core feature that would otherwise mutate persistent user/channel state is observation-only for a trial; record its proposed effect instead. Existing infrastructure throughput and latency measurements include trial traffic.

The fleet `messages_processed` total includes trial messages because Sesame decoded them; its existing meaning remains "decoded," not successful completion. Trial processing never increments normal per-channel counters, `commands_answered`, or `mod_actions`; proposed trial effects get separate metrics. The admin page separately reports unique chat messages received, decoded envelopes, completed processing attempts, retries/errors, average processing latency, and blocked action count. Squashed cohorts may contain many chat messages but count as one envelope, so those values must not be conflated. Trial history has an explicit retention policy in the trial store and is never imported into a registered account's counters. The public per-channel leaderboard excludes trial IDs.

Outgress rejects every action carrying `origin=trial` before action dispatch, including batch children and internal actions that would call Twitch. Outgress also uses current trial IDs, including off rows and stopping tombstones, as a secondary stop switch. The explicit origin marker is the primary invariant: removing an ID cannot release a queued trial action. The secondary switch clears only after removal fences admission and subscription deletion is confirmed; switching a row off keeps the switch in place. It does not wait for normal enrollment, which a new user may leave disabled indefinitely. The stop switch fails closed when its authoritative state is unavailable. Subscription-management calls are a separate, narrow control path and cannot be mistaken for trial output.

## Promotion to a registered user

The add RPC checks the users-service authority before and after reserving an ID. Ingress also consumes `data.users.changed` and periodically checks current trial IDs, including pending reservations. When a matching row appears, it atomically enters `stopping`, stops forwarding new trial notifications, deletes the trial subscription, and removes the ID from desired trial membership after deletion. Duplicate user-change events or retries are harmless. Already queued trial messages retain `origin=trial` and can never emit actions.

The normal dashboard grant and receive-toggle flow creates the real Conduit subscription. Registration alone does not force that toggle on and the trial transition merely allows existing onboarding to proceed. During any overlap, the shared dedup window uses the chat `event.message_id`; a duplicate does not count or run twice within that window. After trial admission is fenced and deletion confirmed, the secondary ID stop switch clears; trial-origin actions remain blocked indefinitely. The add RPC rejects a real user, and reconciliation removes a registration racing an add. Trial history stays visible to admins but is not imported into the account's per-channel counters.

## Acceptance checks

1. Concurrent adds never reserve more than four distinct IDs; duplicate add/remove operations converge; an already registered ID is refused and a registration racing admission cancels the pending/active trial on reconciliation. New rows start on. An off row retains its slot, display name, and counters until removed.
2. One user-token EventSub WebSocket can subscribe four IDs, handle Twitch-directed reconnect, recover a fresh session after failure/restart, and resubscribe from Valkey without copying or storing OAuth tokens in trial state.
3. A trial Twitch notification enters `Ingress.Dispatcher`, follows normal lane selection including special-user premium routing, reaches Sesame through the current ingress route, and increments fleet processing plus trial counts. Public per-channel ranking and registered-user counters remain unaffected.
4. Chat, slash commands, moderation, clips, batches, and delayed outputs cannot make a Twitch call when the originating event is trial, even if its ID was removed between ingest and outgress.
5. Registration while a trial message is in flight stops new trial delivery and allows normal onboarding to proceed; no trial action emits. Overlapping copies with the same chat `event.message_id` process once inside the bounded dedup window.
6. Token/Valkey/Twitch errors appear as bounded per-row failures, and removal or promotion eventually reconciles after the dependency recovers.
7. The overview fleet preview and full Shards page show each active trial by Twitch display name, with broadcaster ID as supporting detail. A trial row is visibly distinct from Conduit shards and does not affect shard scaling counts or utilization.
8. Turning a channel off immediately stops admission on both the trial socket and overlapping Conduit path, deletes its subscription, and keeps its configured row. Turning it on again resubscribes without a duplicate subscription, including when the toggle races an in-flight deletion. No environment flag must be changed to activate a newly added channel.

Run targeted Elixir, Go, and admin web tests, then the relevant build/type checks. Before enabling an AutoMod V2 route, add its provenance and read-only tests.
