# Watchtime implementation and rollout

The watch clock now stores due windows, pagination progress, immutable pending pages, versioned session ownership, successful live confirmations and retry state in primary Valkey. An atomic tenant/session/lease check accepts each page into `watchtime:outbox`. The loyalty service consumes that Stream, transactionally records operation and viewer/window identities with SQL credits, and only then acknowledges/deletes the outbox record. Failed commits are reclaimed; malformed records move to `watchtime:quarantine`.

The collection budget is ten minutes from first claim, independent of an overdue scheduled tick. Unfetched cursor progress expires after that budget. Saved pages remain immutable and can be accepted after reconfirming the same actual Twitch stream; their expired continuation is then discarded. A changed Twitch stream ID clears old pending/cursor work and schedules a fresh window. Accepted outbox awards and previously committed credits remain intact. Live confirmations are still refreshed hourly, so a missed broadcast transition can remain undetected until that check or a versioned lifecycle event.

Chatter RPCs fetch one bounded page per call. They carry an absolute deadline and correlated channel, account generation, session, window and request identities. Four workers and a bounded queue prevent a large listing from monopolizing a subscription. Existing viewer lookups retain their independent, bounded full-list fallback; a watch page warms that cache only when it is the complete first page, so a partial listing never becomes an authoritative viewer snapshot. Every actual HTTP attempt pays the existing shared quota manager, with attendance and tenant shares underneath it. Actual Twitch 429s publish primary-Valkey reset state that gates watch requests across tenants and replicas, separately for app and bot tokens. These bounded identity keys have no TTL so `volatile-lru` cannot discard a live reset; reads retire elapsed resets. The current quota authority is NATS JetStream; Valkey owns watch state rather than running a competing token budget.

## Deployment prerequisites

- Compile/apply the updated JWT account grants from `deploy/messaging/accounts.yaml` using the existing NATS credential rollout: loyalty consumes account change events, and modules can resolve the canonical user's account incarnation.
- The loyalty workload now needs the same Valkey credentials, fleet CA and `valkey-client-tls` secret as the projector. The workload manifest supplies Sentinel/TLS addresses and mounts. Confirm its managed environment includes valid Valkey credentials; do not copy credentials into source control.
- Startup creates `loyalty_account_fences`, `loyalty_watch_operations`, `loyalty_watch_viewers` and `loyalty_watch_retention`. It adds `window_started_at_ms` and a cleanup index to older watch ledgers. The database identity needs table/index creation and alteration permissions. Size this migration against existing history before rollout. Existing Ent balance/counter schema stays in place.
- The updated Valkey StatefulSet requests a retained 8Gi claim for each member. Confirm that the cluster's default StorageClass can provision these claims and that backup/restore covers them. Node-local storage retains node affinity; a lost node still requires storage recovery or replacement of that member from a surviving replica.

Valkey's existing AOF policy remains `appendfsync everysec`, with asynchronous replication and `min-replicas-to-write`. This improves survival of ordinary pod replacements but does not promise zero loss on every disk/failover scenario. [Valkey persistence](https://valkey.io/topics/persistence/).

## Storage transition

The existing StatefulSet uses `emptyDir`. Moving to claim templates is a storage migration, not an ordinary image rollout. Kubernetes supplies stable storage through StatefulSet claims; do not delete an old pod's temporary data before the migration has a verified durable copy. [Kubernetes StatefulSet storage](https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/#stable-storage).

Before enabling the new producers, preserve the current primary's AOF/RDB and verify a restore on retained storage. Recreate/transition the StatefulSet under a maintenance procedure appropriate to the cluster, retaining claims and bringing up one authoritative recovered primary before replicas. Validate Sentinel discovery, TLS, AOF loading and replication before resuming producers. This change has not been applied to a running cluster by the implementation task.

## Account and configuration bootstrap

Canonical user events and projection replies carry `account_created_at` in Unix microseconds and a monotonic `state_revision`. The users service migrates existing rows to revision one; its existing Ent mutation hook increments revisions with source updates, including bulk and transactional writes. A persistent admission record distinguishes an account's current incarnation from an earlier deleted incarnation and retains the last revision even if settings expire. Older or unstamped state cannot undo a known newer pause/ban. Unknown-incarnation deletes are ignored once the current account is known; stamped old deletions also cannot mutate its replacement. Pause/ban/config changes revoke the prior award generation.

Canonical user and stamped loyalty-module projection writes use the same existing account restoration operation. Cold hydration can therefore establish admission without waiting for a user event, and either section may finish first without losing the other's loyalty state. Every final write still checks incarnation/deletion state, so a concurrent deletion or recreation remains fenced.

The permanent admission record also retains `loyalty_revision`. Both module-event and full-snapshot writes refuse older loyalty settings after the settings hash expires. Full hydration preserves a trusted warm revision even if an older snapshot omits loyalty. If a known loyalty row is missing, hydration stays incomplete until a current canonical snapshot restores it. Strictly newer account restoration resets this revision sequence. Drain old projection writers before relying on this fence; they do not understand the permanent revision.

Old warm projections have no incarnation proof. Reproject the canonical users and bootstrap admission before expecting watch clocks to arm. Existing loyalty configurations also need a canonical source-incarnation stamp. After old module writers have drained, verify ownership and resave the full configuration through the new modules service, preserving the enabled flag. A partial patch across an unknown/different incarnation intentionally clears the prior configuration rather than inheriting it. The schema has no trustworthy module creation timestamp for an automatic backfill. Do not bind rows belonging to a retired account to its replacement merely because the Twitch ID matches. Unstamped or stale loyalty configurations deliberately fail closed.

Coordinate the worker/outgress rollout: old chatter replies lack the correlation, actual stream ID/start and pagination contract, and old clocks do not send the new request identities/deadline. During an overlap, mismatched versions skip/retry attendance rather than credit an unverified list. Drain legacy watch producers before restoring clocks on the new path. All producers and SQL consumers must understand the retirement barrier before enabling history maintenance; an old writer/consumer can bypass it. Subscription/bits earnings retain current main's existing idempotent counter-batch transactions, now guarded by the account deletion fence. This change does not migrate the whole points economy into Valkey.

The incarnation fences in this PR cover watch admission, loyalty posting and modules cleanup. Other existing user-deletion consumers, including commands/fetches, still delete by Twitch user ID and require a broader account-cleanup audit before claiming system-wide recreation isolation.

## Operational checks

1. Verify an active, enabled, non-trial channel has an admission incarnation and a `loyaltick:state:<id>` record with a due-set member.
2. Confirm pages advance through a listing larger than the previous 30-page cap without re-crediting overlapping viewers.
3. Stop a worker after a pending page is saved. Its replacement should reclaim the same page/window and SQL should credit each viewer once.
4. Pause, ban or disable loyalty during a request. The next HTTP attempt and award acceptance must be refused. Resume only after canonical projection catches up.
5. Deliver an old offline event after a newer online. The newer session's schedule must remain active.
6. Delete an account with pending awards, then recreate it. Old work must remain retired and new work must use the new account incarnation.
7. Inject a SQL failure. Outbox records must remain pending and recover when SQL returns. The `watchtime` health check reports awards queued for more than five minutes.
8. Return a provider 429 for one watch tenant. Another tenant on another replica must make no HTTP attempt or quota charge until the shared token reset; an app-token cooldown must not block a bot-token page.
9. Block token refresh, then revoke the tenant or expire a waiting caller's deadline. No HTTP attempt should escape either condition. Hold a 429 response body open; shared reset state must already be visible at response headers.
10. Recover after two hours with an unfinished listing. Preserve accepted awards and immutable saved work for the same actual broadcast, but abandon the remaining stale cursor. Change the actual stream ID without local offline/online events and verify old pending work is refused.
11. Deliver an older active user snapshot after a newer pause/ban, including after settings expiration. Admission must stay revoked. Deliver an unstamped deletion after account recreation and preserve the new account.
12. Disable loyalty or change payout settings, expire the projected settings hash, then replay older module events/snapshots. Admission must not reopen with the old configuration. An empty stale snapshot must keep missing known loyalty state eligible for fresh hydration.

Inspect `watchtime:quarantine` when malformed awards are reported. Preserve records for investigation rather than manually acknowledging unpaid work. Do not independently expire or trim outbox records, operation digests, `watchtime:outbox:windows`, or `watchtime:retention:floor`.

History maintenance runs within the existing consumer loop every ten seconds. The seven-day cutoff is capped below every unpaid window by the atomic outbox index. Unindexed legacy deliveries block advancement until consumed. Valkey publishes a permanent admission floor first; SQL then advances a monotonic retirement watermark before deleting bounded batches outside that lock. Both layers refuse retired windows, so deleting old replay markers cannot make a late retry payable. Source window milliseconds and SQL posting age both constrain cleanup. SQL failure can extend retention for as long as accepted unpaid work exists. The configured batch ceiling is a bound, not measured MySQL throughput; monitor cleanup against incoming ledger growth.

Existing structured debug logs expose collection/due age, overdue intervals and page duration, plus SQL commit latency and outbox delivery age. Request rejection carries correlated tenant/window/request and retry state. The existing watchtime health check reports oldest accepted work exceeding five minutes. Enable/sample debug telemetry for acceptance exercises; due state is also inspectable in primary Valkey. No additional metrics client, scheduler or quota authority was introduced.

## Verification status

Touched-package tests, real-Valkey recovery/isolation tests and targeted race checks cover the implemented failure boundaries. SQLite tests exercise retention, replay rejection and older-ledger migration. Scheduler fairness coverage proves page yielding between two tenant sizes; it is not a sustained fleet load measurement.

`app/db/loyalty/repository/watchtime_mysql_test.go` supplies opt-in real-MySQL tests using `MYSQL_TEST_DSN`. Use a disposable server identity with `CREATE DATABASE` permission: tests create and drop their own uniquely named database and do not mutate the DSN's configured database. Run `go test ./app/db/loyalty/repository -run TestWatchMySQL -count=1 -v` with that variable set through the normal secret-safe test environment. Tests cover duplicate full 1,000-viewer chunks across tenants within the ten-second consumer deadline, retirement/posting/deletion races, recreation with legacy flush and pruned replay. These tests were not executed here because MySQL and Docker's daemon are unavailable. Production failover, retained-storage restore and sustained quota/coverage exercises still require the deployment environment.

Watchtime remains an estimate of connected chat presence. Recovery resumes one persisted unpaid window and then schedules the next; it does not invent every missed interval from a later snapshot. The configured window is five minutes, with bounded pagination and retry delays. Twitch's chatter list does not establish actual video playback or continuous viewing.
